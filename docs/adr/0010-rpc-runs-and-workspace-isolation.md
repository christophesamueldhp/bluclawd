# Run subagents through pi RPC with workspace isolation

On 2026-11-10, the user accepted pi RPC as the direction for running subagent sessions and workspace isolation for delegated work, to retain pi's execution model while reducing idle-process overhead and conflicting edits. This revises ADR-0006's requirement that every run be an interactive pi in tmux and ADR-0003's shared-checkout-only decision. It is implemented: since #311 every new run runs on pi's RPC, and no run starts in tmux.

## Accepted behavior

The user's requirements preceding the interview are to target pi 1.5.2, support single runs, parallel `tasks`, sequential `chain` and per-run `cwd`, and preserve pi's efficient execution model. Children may use codemode but may not delegate further or bypass the orchestrator's authority through nested tools, shell commands or messages. Effective capabilities are bounded by the orchestrator's permissions, the role and the specific assignment, not merely by prompt instructions.

- A run can exchange messages with its orchestrator while working. Once it has reported and has no queued instructions, its process ends; its session, context and artifacts remain available for resume.
- Work granted write access uses an isolated worktree. Read-only exploration can use an existing workspace; a reviewer can inspect a writer's workspace after the writer stops writing. A reader that needs a stable view can use a separate snapshot.
- An isolated workspace starts from the relevant local state captured at admission, including applicable uncommitted changes, without an automatic commit. Later orchestrator edits do not appear in it automatically. Ignored files such as `.env` are not copied automatically; additional local files require need and authorization.
- The default is four active subagent executions shared across orchestrators in one Bluclawd daemon on a machine, with fair scheduling. There is no fixed total-run quota; additional runs queue, and stored sessions do not occupy execution slots. The user can configure concurrency; the orchestrator cannot raise it itself.
- Independent orchestrators communicate only after the user opens collaboration between specified sessions for a particular piece of work. Within that scope, relevant findings, questions and blockers need no permission per message. Automatic discovery of collaborators, broadcasting and communication outside the authorized group are excluded.

- The orchestrator may inspect and integrate run changes within the user's authorized scope without confirmation for each application. Integration is serialized, detects changes since the baseline, preserves user edits, and includes combined validation. Routine conflicts may be resolved by the orchestrator; changes of intent return to the user. This does not authorize automatic commits, pushes or discarding changes.
- A worker, reviewer and repair sequence shares one isolated workspace sequentially, with each step's own permissions and no concurrent writers. Review findings may feed a repair step; they are not themselves execution failures. Failed, cancelled or blocked steps halt the chain, and integration follows completion of the sequence.
- Cancelling foreground work stops the associated run and its executing subprocesses; cancelling a batch or chain also cancels its queued steps. Sessions and partial changes are retained. Continuing in the background is a distinct operation. User-cancelled runs require an explicit resume instruction and cannot restart from late messages.
- Approval requests that the policy permits are surfaced in the orchestrator with the run identity, action and target. Existing authorization is reused; a role's hard capability ceiling cannot be widened through an approval request. With no approval channel, work requiring approval is blocked.
- The user can inspect a run's conversation and send it instructions directly through Bluclawd. Instructions reach the same session at a safe boundary when busy, and the orchestrator is informed. This does not require a full interactive pi terminal or support for every pi slash command.

- Keep explorer, reviewer and general-purpose as the bundled roles. Explorer and reviewer have read tools and codemode but no shell or mutation capabilities, including through nested calls. Test execution belongs to a role explicitly authorized to execute commands. A planner may be defined when needed but is not a mandatory stage.
- New runs start with fresh context and an orchestrator-provided task, without automatically copying the parent conversation. Continuing prior context requires explicitly addressing an existing run; reusing a role name does not reuse a session. Independent review uses a new run.
- Single runs, batches and chains default to foreground waiting. Background execution is selected for independent work or at the user's request. Ordinary progress does not repeatedly wake the orchestrator; important messages, blockers and approval requests remain deliverable during work. Foreground waiting does not serialize independent runs in a batch.
- If the orchestrator crashes, an active run may finish its admitted work and store its Report. Queued runs and subsequent chain steps wait for the orchestrator to return and revalidate scope and permissions. Uncertain side effects are reported rather than automatically replayed; explicit user cancellation remains distinct from a crash.
- The first RPC release preserves read access to old tmux-run transcripts and reports but need not resume those runs on the new backend. Active old runs must finish or be explicitly stopped before migration. Continuing their work on RPC starts a new run with newly checked permissions and configuration; RPC-native runs support full resume.

- Resolve roles in this order: invocation-local inline definition, nearest trusted project definition, user definition, bundled definition. Project discovery stops at the repository or workspace root. Scope filtering cannot grant trust; invalid or ambiguous definitions fail rather than silently falling back. Snapshot the effective definition at admission, without allowing later role-file changes to modify active runs or widen resumed capabilities. The model cannot disable trust checks with `confirmProjectAgents`.
- Resolve model and thinking independently from explicit orchestrator choice, then role configuration, then the parent's value. Reject unavailable or incompatible combinations without silently changing the model, provider or thinking level. Freeze the resolved pair at admission; resume preserves it unless the orchestrator explicitly changes it and the new pair passes admission.
- Reports delivered automatically to the orchestrator contain status, a concise summary, changes, actual checks, blockers and references to complete evidence. Target roughly 1,000-2,000 tokens per report, without a minimum length, and bound aggregate batch output. Every run's status remains visible; truncation is disclosed and full evidence remains accessible. Routine reporting does not invoke an extra summarizer model.
- Preserve workspaces containing changes, including after failure or cancellation, until the user explicitly requests cleanup. Unchanged workspaces may be cleaned automatically once unused; transcripts and Reports remain stored. Do not add automatic reconstruction of changed workspaces in the first version merely to save disk space.
- In the first version, read-only work may run outside Git. If a writing run cannot obtain its required isolated worktree, reject it with an explanation instead of silently writing in a shared workspace. Isolated non-Git writing is outside this version's scope.

- Failure of an independent run does not cancel its batch siblings. The orchestrator receives every run's status, available successful results and failure information; explicit cancellation of the whole batch still cancels all its work. Chains retain their dependency-based halt behavior.
- Resume requires the original workspace or an exact restoration of its required state. Automatically clean an unchanged workspace only when that state is recoverable; otherwise retain it. If explicit user cleanup leaves a changed workspace unrecoverable, refuse resume clearly while retaining the transcript and Reports as references for a new run. Never silently substitute the latest repository state.
- Stop requests cancellation of active work while preserving its session and partial changes. Resume and workspace cleanup remain distinct operations. Do not expose `subagent_close` to the model or require the orchestrator to manage idle process lifetime to release capacity; the runtime owns that lifetime.

The user accepted these behaviors in interview rounds Q1-Q23, after explicitly confirming that communication during work remains available. The subsequent `to-spec` invocation confirmed synthesis and publication, and the user explicitly approved the public RPC, real-OS enforcement and comparative evaluation testing seams. [Issue #290](https://github.com/christophesamueldhp/bluclawd/issues/290) is the implementation specification.

## As implemented

- A run's pi is `pi --mode rpc -ne` with bluclawd's child extension (`ext/subagents/rpc-child.ts`), its tools as an allowlist, its exact provider, model and thinking level, and the orchestrator's agent dir, so pi's built-in providers, `models.json` and `auth.json` reach it. A detached host per run (`ext/subagents/rpc-host.ts`) is the only holder of its stdio; the daemon's queue (`daemon/run-queue.ts`) starts the host once a slot is free.
- A provider an extension of the orchestrator's pi registers is not loaded in the child, so a run of one is refused at Admission. `BLUCLAWD_RPC_PROVIDER_EXTENSIONS` lists extensions the child loads besides; it is a stopgap for tests and development, not a supported configuration.
- A role's tools are what a run may have; one naming none only reads. A tool named with a trailing `?` is given only where it can be; the bundled `general-purpose` names its tools that way, rather than being recognized by name.
- Shell commands are contained, and their processes confirmed ended, only on macOS. On Linux and WSL a run gets no shell: a role naming `bash` is refused, and `general-purpose` edits without running commands. This conflicts with ADR-0001's statement that only a VM can contain a process's lifetime on macOS, which is for the user to settle.
- Recovery (#308). A host outlives its orchestrator and the daemon. A host takes its generation exclusively (`hosts/<generation>` in the run directory), so a host launched twice leaves it to the first, and an orchestrator follows whichever holds it. On `session_start`, the session takes its open runs over from their run directories (`definition.json` or `generations/<n>.json`, and `rpc-spec.json`): a run whose host holds its generation is followed and its Report delivered once; one never started queues again, rechecked against the session as it is now; one whose host ended with no Report fails as uncertain and is never replayed. A reload hands its runs to the next instance, which relays, answers and stores from then on. The daemon stores the runs it launched in `run-slots.json` and keeps their slots across a restart. A chain's plan is in `chain-plans/<id>.json`, from which a reopened session continues it. Collaborations, remembered approvals and the queue's waiting runs live only in memory.
- Migration. Runs in tmux from before stay readable: their transcripts and Reports are kept, and opening a finished one shows its conversation. One still open when its orchestrator's session starts again is taken over in its pane (ADR-0008) and kept until it is stopped or that session ends, never ended silently. None is resumed: a Resume or message to one points at its Report and transcript for a new run, admitted afresh. Nothing starts a run in tmux any more, and `subagent_close` is gone.
